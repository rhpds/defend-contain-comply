# Module 02: CONTAIN -- Policy-Gated Remediation

### Brief Overview

This module introduces policy-as-code into the remediation workflow. Participants create OPA (Open Policy Agent) patch policies that define conditions under which remediation can proceed, then build a 5-node AAP workflow that incorporates an approval gate and a policy-as-code execution check. The workflow runs a pre-patch validation playbook, pauses for human approval, evaluates OPA policies before proceeding, and executes the patch. Participants run the full workflow end-to-end, review compliance reports, and then intentionally violate a policy to observe the workflow halt at the execution gate.

### Audience and Time

- **Target personas:** Security engineers, platform engineers, compliance-focused system administrators
- **Prerequisites for this module:** Completion of Module 01 (DEFEND), familiarity with AAP workflow concepts
- **Estimated duration:** 40 minutes

### Learning Objectives

- Build a 5-node AAP remediation workflow with approval gates and OPA policy execution checks
- Configure OPA patch policies that enforce pre-conditions before remediation proceeds
- Verify policy-as-code enforcement by demonstrating both successful execution and policy violation scenarios

### Lab Structure

| Section | Title | Duration |
|---------|-------|----------|
| 1 | Create OPA patch policy on the central node | 5 min |
| 2 | Build pre-patch check playbook in AAP | 5 min |
| 3 | Construct 5-node AAP workflow with approval gate | 8 min |
| 4 | Add OPA policy-as-code execution gate to the workflow | 5 min |
| 5 | Execute end-to-end remediation workflow | 7 min |
| 6 | Review compliance reports | 5 min |
| 7 | Demonstrate policy violation and workflow halt | 5 min |

### Detailed Steps

1. SSH to the central node and create an OPA patch policy that defines allowed patch windows, required pre-conditions (backups, maintenance mode), and permitted target hosts.
2. In AAP Controller, create a pre-patch check job template that validates system state (disk space, running services, backup status) before patching.
3. Build a new workflow template in AAP with 5 nodes: pre-patch check, approval node, OPA policy evaluation, patch execution, and post-patch validation.
4. Configure the approval node to require manual approval before the workflow continues past the validation stage.
5. Add the OPA policy evaluation step that queries the OPA server on the central node. Configure the workflow to halt if the policy returns a deny decision.
6. Run the complete workflow against rhel01. Approve the request when prompted. Observe each node executing in sequence and the final patch applying.
7. Review the compliance report generated by the post-patch validation node. Verify the report shows all checks passed.
8. Modify the OPA policy to introduce a condition the current environment violates (e.g., restrict the patch window to a past time).
9. Re-run the workflow. Observe that the OPA execution gate halts the workflow before the patch step executes.
10. Review the workflow output to confirm the policy violation message and the workflow's graceful halt.

### Key Takeaways

- Policy-as-code with OPA provides auditable, version-controlled guardrails for remediation workflows
- Approval gates add human oversight at critical decision points without blocking automation
- AAP workflows can enforce multi-step validation pipelines that prevent unauthorized or unsafe changes
- Policy violation demonstrations prove the guardrails work and build stakeholder confidence

### Infrastructure Notes

- OPA server runs on the central node and is pre-configured with a baseline policy bundle
- The AAP Controller workflow editor is used to construct the 5-node workflow visually
- Pre-patch check playbook validates system health before remediation proceeds
- Compliance reports are generated as HTML and accessible via the compliance portal on the central node
